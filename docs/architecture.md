# Архитектура проекта

## Общий принцип
Проект строится как три независимые части, которые соединяются через общий API и единый контракт данных:

- Frontend — пользовательский интерфейс, симуляция и визуализация;
- Backend — валидация, логика расчёта и API;
- ML — вычисление итогового score и AI-объяснение.

## Контракт данных
### 1. Состояние города
- бюджет_total
- бюджет_remaining
- районов: массив объектов
- показатели по категориям:
  - transport
  - greenery
  - social
  - safety
  - services

### 2. Мероприятия
Каждое мероприятие включает:
- id
- category
- title
- cost
- impact
- target_zone
- description

### 3. Результат симуляции
- total_score
- category_scores
- risks
- strengths
- recommendations
- budget_status

## Поток данных
1. Пользователь открывает страницу симулятора.
2. Frontend запрашивает список районов и мероприятий.
3. Пользователь выбирает решения и нажимает “Запустить расчёт”.
4. Backend проверяет бюджет и формирует payload.
5. Backend отправляет payload в ML-модуль.
6. ML возвращает score, сильные стороны, риски и рекомендации.
7. Backend возвращает итоговый результат в frontend.
8. Frontend показывает итоговый dashboard.

## Логика расчёта score
Формула может быть реализована в виде взвешенной суммы ключевых показателей:

Astana Quality of Life Score =
0.25 * transport + 0.20 * greenery + 0.25 * social + 0.15 * safety + 0.15 * services

Затем результат корректируется на:
- бюджетные ограничения;
- дисбаланс между районами;
- риск перегрузки инфраструктуры;
- неэффективное распределение инвестиций.

## UI-архитектура
Frontend должен быть построен вокруг 3 ключевых блоков:
- слева: список решений по 5 категориям;
- центр: карта/панель районов и остаток бюджета;
- справа: итоговый score и AI-пояснение.

## Принцип модульности
Все части должны быть независимыми, но взаимодействовать через стандартный API JSON. Это упрощает сборку, тестирование и совместную работу команды.
